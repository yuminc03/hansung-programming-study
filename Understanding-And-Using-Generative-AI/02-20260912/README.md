# 사내 IT 헬프데스크 문의 자동 배정 대시보드
문장의 의미를 숫자로 바꿔 비교하는 임베딩 기술로, 들어온 문의를 담당팀에 자동으로 배정하고 확신이 낮은 건은 사람에게 넘기는 웹 대시보드입니다.

## 무엇을 자동화했는가
사내 IT 헬프데스크에 접수된 문의를 사람이 하나씩 읽고 담당팀을 정하던 분류 업무를, FAQ 12건과의 의미 유사도 계산으로 대체했습니다.

기존에는 접수 담당자가 문의를 읽고 계정 문제인지 네트워크 문제인지 판단해 각 팀으로 넘겼습니다. 이 대시보드는 문의 20건을 한 번에 붙여 넣으면 즉시 배정표를 만들어 줍니다. 실제 측정에서 20건 중 19건이 자동 배정됐고, 1건만 사람 확인으로 남았습니다.

## 기술 스택
| 구분 | 사용 기술 | 선택 이유 |
|---|---|---|
| 임베딩 모델 | BAAI/bge-m3 (1,024차원) | 한국어 성능이 검증된 다국어 모델. API 키 없이 로컬 CPU에서 실행 |
| 유사도 계산 | scikit-learn cosine_similarity | 문장 길이에 흔들리지 않고 방향만 비교 |
| 화면 | Streamlit | 파이썬만으로 웹 UI 구성. 모델 캐시 기능 내장 |
| 시각화 | Altair | 브라우저가 글자를 직접 그려 한글 축 라벨이 깨지지 않음 |

외부 API를 쓰지 않으므로 문의 내용이 회사 밖으로 나가지 않습니다. 사내 데이터를 다루는 업무에서 중요한 조건입니다.

## 전체 흐름과 구현 위치
문장이 담당팀으로 바뀌기까지 네 단계를 거칩니다. 각 단계가 어디에 구현돼 있는지 아래에 정리했습니다.

| 단계 | 하는 일 | 구현 위치 |
|---|---|---|
| 1. 토큰화 | 문장을 모델이 처리하는 작은 단위로 나눔 | 노트북 3절에서 원리 확인. 대시보드에서는 모델 내부에서 자동 처리 |
| 2. 임베딩 | 문장 1개를 숫자 1,024개로 변환 | [app.py:81](app.py#L81) FAQ 측, [app.py:94](app.py#L94) 문의 측 |
| 3. 유사도 | 문의 N건 × FAQ 12건 행렬 계산 | [app.py:124](app.py#L124) |
| 4. 배정 | 최고점 FAQ의 담당팀을 가져오되 기준값으로 거름 | [app.py:126](app.py#L126) 정렬, [app.py:135](app.py#L135) 판정 |

### 토큰화를 대시보드에서 따로 다루지 않은 이유
토큰화는 임베딩 모델이 문장을 받는 순간 내부에서 실행됩니다. 별도로 호출할 필요가 없습니다.

다만 원리를 이해하는 것은 중요합니다. 토큰 수가 곧 API 비용이자 모델이 한 번에 읽을 수 있는 분량이기 때문입니다. 같은 뜻이라도 한국어는 영어보다 토큰을 더 씁니다.

```
주문한 상품은 언제 배송되나요?              한국어 10토큰
When will my order be delivered?           영어    7토큰
```

이 대시보드가 FAQ 전체를 통째로 넘기지 않고 비슷한 것만 골라 쓰는 구조인 이유도 여기에 있습니다. 노트북 7절 기준으로 FAQ 12건 전부는 159토큰, 가장 비슷한 1건만 고르면 10토큰입니다. 94퍼센트를 아낍니다. FAQ가 1만 건으로 늘어나면 이 차이가 그대로 비용이 됩니다.

### 핵심 코드
배정 로직은 세 줄로 요약됩니다.

```python
similarity = cosine_similarity(inquiry_vectors, faq_vectors)   # 문의 N건 × FAQ 12건
ranking = np.argsort(-similarity, axis=1)[:, :TOP_K]           # 상위 3개 위치
team = faq.loc[best, "담당팀"] if best_score >= threshold else UNASSIGNED
```

모델을 학습시키지 않았다는 점이 중요합니다. 이미 담당팀이 적혀 있는 FAQ를 기준 삼아, 가장 가까운 것의 라벨을 복사해 옵니다. 최근접 이웃 분류와 같은 구조입니다. FAQ 표만 바꾸면 다른 업무에 그대로 쓸 수 있습니다.

## 기준값이 왜 필요한가
최고 유사도가 0.55보다 낮으면 담당팀을 정하지 않고 '담당자 확인'으로 넘깁니다. 이 한 줄이 이 프로그램에서 가장 중요한 설계입니다.

### 기계는 "모른다"고 말하지 못한다
가장 비슷한 것을 고르는 연산은 후보가 전부 무관해도 반드시 답을 내놓습니다. 12개 FAQ가 모두 엉뚱해도 그중 최댓값은 존재하기 때문입니다.

즉 **"가장 비슷한 것"과 "충분히 비슷한 것"은 전혀 다른 말**인데, 최고점만 고르는 방식으로는 이 둘을 구분할 수 없습니다. 사람이 점수에 하한선을 그어 거절 구간을 만들어 줘야 합니다.

### 실제로 걸러진 것
실행 결과 "구내식당 이번 주 메뉴는 어디서 보나요?"가 걸러졌습니다. IT와 무관한 총무 영역 문의입니다.

| 항목 | 값 |
|---|---|
| 최근접 FAQ | F1. 사내 시스템 비밀번호를 잊어버렸어요 |
| 유사도 | 0.46 |
| 판정 | 담당자 확인 |

기준값이 없었다면 구내식당 문의가 계정관리팀으로 배정됐을 것입니다. 엉뚱한 팀이 확인하고 되돌려 보내는 동안 응답이 늦어지고, 문의자는 방치됐다고 느낍니다. 사람이 한 건 직접 읽는 비용보다 훨씬 비쌉니다.

### 0.55라는 값의 근거
이론적으로 도출된 상수가 아니라 관측된 분포에서 정한 값입니다. 정상 배정 건은 0.55에서 0.93 사이에 몰려 있고, 무관한 문의만 0.46으로 떨어져 있습니다. 그 사이 빈 구간에 선을 그었습니다.

데이터나 모델이 바뀌면 다시 조정해야 하므로, 코드에 고정하지 않고 사이드바 슬라이더로 0.3에서 0.9까지 움직일 수 있게 했습니다.

| 기준값 | 자동 배정 | 담당자 확인 |
|---|---|---|
| 0.55 | 19건 | 1건 |
| 0.90 | 2건 | 18건 |

기준값을 올린다는 것은 기계를 더 의심한다는 뜻이고, 그만큼 사람이 볼 일이 늘어납니다. 이 맞바꿈을 슬라이더로 직접 만져 보게 한 것이 이 화면의 의도입니다.

## 이 방식이 잡아내지 못하는 것
기준값은 완전히 무관한 문의만 걸러 냅니다. **비슷한 것들 중에서 엉뚱한 것을 고른 경우는 통과시킵니다.** 실행 결과에서 확인한 실제 사례는 다음과 같습니다.

- **FAQ에 없는 주제인데 통과** — "퇴사자 계정은 언제 삭제되나요?"가 0.55로 간신히 통과해 계정관리팀으로 갔습니다. 팀은 맞지만 FAQ에 퇴사자 계정 항목이 없어 비밀번호 분실 항목에 붙은 것입니다.
- **주제만 맞고 절차가 다름** — "회사 메일을 휴대폰에서도 보고 싶습니다"가 메일함 용량 FAQ에 붙었습니다. "메일"이라는 주제만 맞췄을 뿐 모바일 설정과 용량 관리는 다른 절차입니다.
- **고장과 신청을 구분하지 못함** — "키보드에 안 눌리는 자판이 몇 개 있어요"가 주변기기 신청 FAQ에 붙었습니다. 수리 요청과 신규 지급은 처리 방식이 다릅니다.

세 건 모두 담당팀은 우연히 맞았습니다. 한 팀이 여러 주제를 맡고 있어서 가려졌을 뿐이고, FAQ가 늘어나면 실제 오배정으로 드러납니다.

이 밖에 구조적으로 다루지 못하는 경우가 더 있습니다.

- **한 문의에 주제가 둘 섞인 경우** — 노트북 고장과 VPN 문제를 함께 물으면 하나의 팀만 배정됩니다.
- **FAQ에 없는 신규 이슈** — 새로 도입된 시스템 문의는 기존 FAQ 어디에도 가깝지 않아 계속 사람에게 넘어갑니다. FAQ를 갱신해야 한다는 신호로 읽어야 합니다.
- **표현은 비슷한데 뜻이 반대인 경우** — 임베딩은 주제의 근접성을 보므로 긍정과 부정을 항상 구분하지는 못합니다.

### 보완 방향
1등과 2등의 점수 차이를 함께 보는 방법이 있습니다. 차이가 작으면 판단이 아슬아슬했다는 뜻이므로 사람에게 넘길 후보입니다. 지금은 상위 3개를 가로 막대로 보여 주어 담당자가 눈으로 확인할 수 있게 했습니다. 기준선을 점선으로 함께 그려 1등이 선을 넘었는지 바로 보입니다.

## 실행 방법
```bash
cd Understanding-And-Using-Generative-AI/02-20260912
pip install streamlit sentence-transformers scikit-learn pandas altair
streamlit run app.py
```

첫 실행에서 임베딩 모델 약 2.2GB를 내려받습니다. 그 뒤로는 캐시를 재사용하므로 바로 뜹니다.

## 성능을 위해 한 일
Streamlit은 위젯을 건드릴 때마다 스크립트 전체를 다시 실행합니다. 아무 조치가 없으면 슬라이더를 한 칸 움직일 때마다 2.2GB 모델을 다시 읽게 됩니다.

- **모델과 FAQ 벡터** — `st.cache_resource`로 감싸 프로세스 전체에서 한 번만 만듭니다. FAQ는 고정이므로 그 벡터도 재계산할 이유가 없습니다.
- **문의 임베딩** — `st.cache_data`로 캐시합니다. 같은 문의 목록이면 다시 계산하지 않으므로, 기준값 슬라이더를 움직일 때는 비교 연산만 다시 합니다.

덕분에 기준값을 바꿔도 화면이 즉시 반응합니다.

## 배운 것
- 임베딩은 글자가 아니라 의미를 비교합니다. "택배가 아직 안 왔어요"와 "주문한 상품은 언제 배송되나요?"는 겹치는 단어가 없는데도 유사도 0.70이 나옵니다.
- "임베딩 → 유사도 → 가장 비슷한 것 선택"은 검색과 추천, 문서 질의응답(RAG, Retrieval-Augmented Generation)의 공통 뼈대입니다. 이 프로젝트는 그중 검색 단계에 해당합니다.
- 가장 중요한 것은 자동화의 범위를 정하는 일이었습니다. 기계는 비슷한 것을 찾을 뿐이고, 확신 없는 판단은 사람에게 넘겨야 합니다. 그 경계를 슬라이더 하나로 드러낸 것이 이 프로젝트의 핵심입니다.
